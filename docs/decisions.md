| 47 | S5 ID agent: identifier fields, fingerprints and cross-system matches | assumed, pending Yashaswi | After each profile, the ID agent treats as identifier fields every column tagged `identifier` plus the key columns joined by trusted references (declared, or inferred with at least 0.98 coverage). It reads each field's distinct values in the worker or API process, stores only keyed fingerprints (HMAC-SHA256 with a per-tenant key derived from `ARTIFACT_MASTER_KEY`, non-negotiable 6), and discards the values; fields with more than 1,000,000 distinct values are listed but not fingerprinted. A field's fingerprints are replaced on each profile. Across connections it proposes one probable `SAME_AS` per field and other source: at least 20 shared values, at least 98% of the smaller set matched, the same value format, and the closest set size among candidates (this separates patient IDs from encounter IDs that are both small integers). Matches are `inferred` with the matched share as confidence and only counts as evidence; they stay probable until reviewed and are never shown as verified. The ID trace screen groups fields by trusted references and these matches, lists only groups that hold a tagged identifier, takes the field with the most values as the origin, and marks a field whose column name differs from the origin's as a changed key. Looking up one value fingerprints it in the API, compares fingerprints from each source's last profile, and never stores, logs or returns the value. Alternatives considered: querying each source live for a looked-up value (rejected for now: needs a parameter-bound query per field per source on every lookup; fingerprints answer the same question from the last profile); matching by Jaccard similarity alone (rejected: a workbook holding one year of encounters is a true subset of the encounter table). | Agent, 25 Nov 2026 |
